Reading a DRAM map by timing

A memory controller's physical-address → (channel, rank, bank group, bank, row, column) layout is undocumented. dram_xlat recovers it from nothing but access latency. Everything below is real output from the solver recovering a known DDR4-style map out of 150,000 noisy timed address pairs.

1 · The signal — a bimodal latency distribution

Two addresses in the same bank but different rows force a row-buffer conflict: measurably slower than two addresses served in parallel from different banks. That split is the entire basis of the method.

row hit / different bank (fast) row-buffer conflict (slow)

2 · Which address bits select the row

Toggle one physical-address bit at a time and re-measure. A pure row bit keeps the bank fixed and changes the row → conflict (slow). Bits that feed a bank/rank function switch banks → fast; low bits stay in the same row → fast.

Simulated single-bit sweep on the example model; on hardware the probe's sweep mode produces exactly this shape.

3 · The recovered translation map

The solver's GF(2) null-space / genetic search returns the XOR functions the controller uses. Here is how the 34-bit physical address decodes, and the five functions recovered — each a 2-bit XOR.

byte offset column bank / rank / group row

4 · XOR structure of the functions

Each recovered function (row) XORs exactly two address bits (columns). The regular 4-bit stride is the controller spreading consecutive rows across banks.

5 · Why three solver routes — robustness vs. noise

As the two timing modes get closer (harder to tell apart), the exact and RANSAC null-space solvers fail first — one mislabeled pair corrupts the linear system. The noise-tolerant genetic search recovers the full map far deeper into the noise.
